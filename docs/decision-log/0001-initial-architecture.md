# 0001 — Initial architecture

- Status: Accepted provisionally
- Version: 1.0.0
- Date: 2026-08-19

## Decision

Build AGAS as a modular monorepo with a Next.js/TypeScript PWA shell, a Python/FastAPI application, a PostgreSQL-oriented SQLAlchemy persistence layer, and explicit Python domain contracts. Keep conceptual planner, evidence, safety, ontology, and evaluation boundaries separate in source while deploying a single backend during early milestones.

Use relational tables for identity, ownership, time, version, and provenance relationships. Use JSON only for flexible context and ontology metadata. Treat observations, capability estimates, and equipment-availability changes as append-only history. Require capability estimates to reference existing same-athlete observations.

Expose only health and metadata endpoints in Milestone 1. Do not create raw CRUD endpoints before application use cases can enforce the domain invariants.

## Reason

The structure matches the master blueprint while keeping the first implementation small, inspectable, strongly typed, and testable. A relational core makes provenance and temporal history enforceable. A single backend avoids operational complexity while the product model is still evolving.

## Major implementation choices

- Pydantic models define transport-independent domain contracts and reject invalid derived-state representations early.
- SQLAlchemy 2 provides explicit relational mappings and supports PostgreSQL in production and SQLite for isolated tests.
- Alembic owns durable schema evolution.
- FastAPI is initially a thin transport and composition layer.
- Next.js App Router provides a minimal responsive/installable web foundation without presenting fake product functionality.
- Python dependencies are managed from one root `pyproject.toml`; JavaScript dependencies use a pnpm workspace.
- Historical observations, capability estimates, their source links, and equipment availability events reject in-place mutation and deletion.
- Capability-estimate source order is persisted explicitly so multi-observation provenance round trips deterministically.
- Ontology references that carry product meaning—exercise-to-adaptation, equipment requirements, progression/regression, and evidence-backed adaptation relationships—use foreign-keyed association tables rather than unchecked JSON identifiers.

## Alternatives considered

### Multiple deployable microservices

Rejected for now. Planner and evidence concepts need clear code boundaries, not independent operational stacks before their contracts stabilize.

### One generic JSON document per athlete

Rejected. It would make provenance links, temporal history, ownership, querying, and safe schema evolution too easy to bypass.

### Vector database as the athlete store

Rejected. Embeddings may later support evidence retrieval, but they are not authoritative structured state.

### LLM-generated plans before deterministic domain rules

Rejected as an architectural failure under the project invariant.

### Complete API CRUD in the foundation milestone

Deferred. Generic CRUD would expose persistence details before assessment and planning use cases define legitimate state transitions.

## Assumptions

- Python 3.12, Node.js 22, and PostgreSQL 16 are acceptable provisional runtime baselines.
- UUIDs are generated by the application to keep domain objects persistence-independent.
- UTC-aware timestamps are mandatory at domain boundaries.
- Semantic versions identify schemas/rules; records also receive immutable database identity.
- SQLite is acceptable only as a test adapter; PostgreSQL remains the intended authoritative store.

## Evidence

This is primarily a software-architecture decision based on the product invariants and recommended stack in `docs/MASTER_BLUEPRINT.md`. It makes no scientific training claim.

## Uncertainty and unresolved questions

- Authentication, tenancy, and data-deletion obligations need a dedicated decision before user accounts are implemented.
- The exact split between domain entities and application command models will evolve with the assessment milestone.
- PostgreSQL row-level security may become appropriate after tenancy is defined.
- Clinical review is required before concrete symptom escalation thresholds are implemented.
- The evidence-review workflow and reviewer identity model remain undefined.

## Consequences

- Later features must enter through domain/application use cases rather than writing database rows directly.
- Historical records consume more storage, but preserve auditability and model evolution.
- Schema changes require migrations and version-aware domain updates.
- Ontology records must be inserted after the adaptations, equipment, exercises, and evidence claims they reference; dangling references fail at the repository and database boundaries.
- The web app remains deliberately sparse until the closed loop produces real user value.
